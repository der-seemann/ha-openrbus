## Counts

- Core registry objects audited: 3066.
- OBD exact-address matches whose exact metadata `Name` contains the token `Zone` (including `parAp…`/`varAp…` system rows): 295.
- Exact positive CP020 slot map: 262 reviewed address keys (OBD object semantics + matching Core array metadata, after excluding documented multidimensional and system-global rows).
- Parent-only function selectors: CP020 array head 3404:00, whose item selectors are 3404:01–:0A per OBD/Core max_items=10.
- Unresolved/excluded: 22 exact Zone-named addresses whose slot dimensions or runtime ownership remain unproven.

- Old heuristic windows cover 180 objects; among 295 exact Zone-name OBD joins, 116 are outside them. The old window includes 5443:00 (`varApSafetyThermostatStatus`), which is not zone-named by OBD and is rejected.

## Limits

This map establishes source-backed projection dimensions, not runtime presence, family support, activity, access, or safe writability. A code/name join does not establish that a specific node implements a slot. Unknown/unread/zero CP020 means no child and no mapped non-selector zone entities. The source proves a general catalog bound of ten, not a universal actual zone count; family maxima and runtime reads remain separate. The 22 unresolved dimensions are also covered by the independent IAE/FunctionGroup audit recorded in `worklog/2026-10-07_zone-dimension-audit-rw-luna.md` and `worklog/2026-10-07_zone-dimension-followup-rw-luna.md`; 340c/3412 have different profile-specific cardinalities from CP020 (EHC-16 `{1}` vs `{1..6}`; SCB-10 `{1..5}` vs `{1..30}`), so their flattened zone/activity order remains unresolved. 340d/3411 likewise use six-entry activity/name dimensions and are excluded. 3406 is family-scoped only to EHC-16/SCB-10. The ten parent-scoped records include six application/discovery records plus 540e/5422/5423/5432; 5422 is an all-zones table, not a local child array.

## Registry cleanup behavior

Projection cleanup uses Home Assistant's public `EntityRegistry.async_remove` only for this config entry's exact mapped unique IDs in the five supported entity domains. It never removes device-registry rows. Source verification used the Home Assistant Core 2026.9.4 wheel (`homeassistant/helpers/entity_registry.py`): `async_remove` saves a `DeletedRegistryEntry` keyed by `(domain, platform, unique_id)`, and `async_get_or_create` restores the entity ID, entity name, area, explicit disabled/hidden state, icon, labels, aliases, options, and registry UUID. Because these rows retain their config-entry ID, their `orphaned_timestamp` is `None`; the 30-day purge applies only after the config entry is removed and the tombstone becomes orphaned. Thus normal inactive/active transitions preserve the tombstone, but removing the integration entry can eventually expire it. Stable child device identifiers reconnect to the untouched device-registry entry, which retains device `name_by_user` and area. This was source-verified, not tested against the live Test-HA registry.
